## Evidence convention

- **Brief-supplied** — stated in the project brief; not independently verified or validated through search data.
- **Recommendation** — proposed SEO, content, or governance direction.
- **Publish gate** — fact, evidence, permission, review, or technical decision required before publication.

The search phrases in the brief are useful intent hypotheses, not proof of search volume, competitiveness, ranking feasibility, or RENZ’s eligibility to make a claim. The expected client source material was unavailable during this pass. No project, credential, location, client, statistic, or professional-registration claim is assumed.

## Search objective

**Recommendation:** Build organic visibility around the decisions a serious prospective client makes before contacting a construction, architecture, or engineering provider in Rwanda:

1. Understand a service or project-preparation requirement.
2. Find a provider whose scope appears relevant.
3. Evaluate credible, comparable work and professional proof.
4. Prepare useful information for a project conversation.

SEO should support the product journey rather than create a parallel library of thin pages. Expertise pages own commercial service intent, Insights answer preparation questions, Projects provide evidence, and Start a Project converts qualified interest.

## Search principles

1. One authoritative canonical page per service.
2. One clear search intent per page, with natural supporting vocabulary.
3. No location doorway pages or duplicated “Rwanda/Kigali” variants.
4. No keyword stuffing, hidden copy, fabricated FAQs, or generated filler.
5. No credentials, outcomes, statistics, review scores, or client names without evidence and permission.
6. Regulatory and cost content is dated, sourced, reviewed, and maintained.
7. Only published, substantial, current content is indexable.
8. Internal links follow real user decisions, not arbitrary keyword targets.

## Canonical page strategy

### Expertise pages

Recommended heading and content hierarchy:

1. Specific H1 using the approved canonical service name
2. Concise scope and audience proposition
3. What the service includes
4. What RENZ needs from the client
5. How the service fits the wider project journey
6. Plain-language process and deliverables
7. Verified relevant projects
8. Reviewed FAQs based on real inquiry patterns
9. Related practical insights
10. Start-a-Project CTA with service preselected

A service record remains draft/noindex when it lacks substantive scope or verified delivery wording. Do not launch ten nearly identical pages simply because the routes exist.

### Project pages

Project SEO value comes from specificity and evidence, not repeating service keywords. Include the approved title, public-safe location, project type, RENZ role, related services, narrative, stages, rights-cleared media, and verified outcomes.

Do not expose confidential addresses or client identities for local relevance. A less precise but approved location is preferable to a privacy breach.

### About

The About page may support branded and local trust queries through verified company identity, operating area, team, method, and credentials. It should not become a dump of keyword-heavy service paragraphs.

### Contact

The Contact page should hold the authoritative public contact details and, if approved, address, hours, service area, map reference, and social profiles. Those details must match all other public instances.

### Filters and pagination

- Project and insight filters use crawl-safe query parameters or client-side state by default.
- Filter combinations are canonicalized to the unfiltered index unless a destination has unique, substantial content and intentional search value.
- Paginated archives use self-canonicals and accessible next-page navigation where pagination is implemented.
- Empty or single-item filter states are not indexable landing pages.

## Metadata system

Each indexable record should support an editorial override while retaining safe defaults.

| Page type | Recommended title pattern | Description focus |
|---|---|---|
| Home | Approved brand proposition + RENZ | What RENZ does and where, using verified wording |
| Expertise index | Expertise + RENZ | Coordinated service journey without unsupported “end-to-end” claims |
| Expertise detail | `{Service} | RENZ` with locality only when accurate and useful | Audience, scope, and next action |
| Projects index | `Projects | RENZ` | Verified project types and evidence, not project counts unless sourced |
| Project detail | `{Project title} | RENZ` | Project type, approved location, RENZ role, and key scope |
| About | `About RENZ` | Verified company identity, method, team, and credentials |
| Insights | `Insights | RENZ` | Practical construction, design, and project-preparation guidance |
| Article | `{Article title} | RENZ` | The specific question answered and review context |
| Contact | `Contact RENZ` | Verified contact and service-area wording |
| Start a Project | `Start a Project | RENZ` | What information to prepare; no quotation promise |

Metadata rules:

- Titles and descriptions are unique, concise, and truthful.
- Local terms appear naturally only where the approved service area supports them.
- Do not place a list of services in every description.
- Social images use rights-cleared media and readable art direction; a generic verified brand image is the fallback.
- Changing a published slug requires a redirect from every known previous canonical path.
- Canonical overrides are exceptional and permission-controlled.

## Structured data

Structured data mirrors visible, verified content. It does not create facts that are absent from the page.

| Page/context | Recommended type | Required source and gate |
|---|---|---|
| Site-wide identity | `Organization`, and an appropriate `LocalBusiness` type only when accurate | Legal/public name, canonical URL, logo, official contact, address/service area, and profiles must be verified. |
| Site home | `WebSite` | Canonical site name and URL. Do not advertise site search unless a real search function exists. |
| Expertise detail | `Service` | Approved service name, description, provider relationship, and actual area served. |
| Insight article | `Article` or `BlogPosting` | Public author/reviewer where appropriate, dates, headline, image rights, canonical publisher. |
| Navigation context | `BreadcrumbList` | Breadcrumbs visible or semantically represented and matching canonical paths. |
| Important image | `ImageObject` when useful | Rights-cleared URL, dimensions/caption/credit as available. |
| Project detail | Conservative `WebPage` plus `BreadcrumbList` and eligible `ImageObject` | Avoid inventing a schema “Project” entity or performance properties not supported by the page. |
| Visible FAQ | `FAQPage` only when technically and editorially appropriate | Questions and answers must be visible, unique, reviewed, and based on real content; rich-result visibility is never promised. |

Never add `Review`, `AggregateRating`, award, price, employee count, founding date, client, credential, or completed-project claim without corresponding approved visible content and evidence.

Structured-data validation is part of pre-release QA, but a validator passing does not make the underlying facts true.

## Technical SEO architecture

### Indexability

- Public draft, preview, archived, expired, private, admin, lead, attachment, and confirmation resources are not indexable.
- Public list/detail routes return a real not-found response when a published record does not exist; avoid soft 404 pages.
- Removed content receives an intentional redirect to a genuinely equivalent page or a proper gone/not-found outcome. Do not redirect every removed page to Home.
- Search crawlers must not be the only protection for private content; authorization remains mandatory.

### Canonical URLs

- Select one HTTPS canonical host after the domain is approved.
- Enforce one case, trailing-slash, and path policy consistently.
- Each indexable page has a self-canonical unless there is a deliberate, reviewed exception.
- Query filters, tracking parameters, and preview tokens never become canonicals.
- Maintain redirect history when published slugs change.

### Sitemap and robots

- Generate the sitemap from published, indexable canonical records only.
- Include accurate modification dates derived from substantive public-content changes, not every background update.
- Reference the sitemap from `robots.txt` after the canonical domain is known.
- Exclude crawl-unhelpful application routes, but never treat `robots.txt` as access control.

### Page semantics

- One primary H1 aligned with the page’s purpose
- Logical H2/H3 hierarchy without headings chosen for visual size
- Descriptive internal link text rather than repeated “Learn more”
- Meaningful image filenames where editorially manageable, plus contextual alt text
- Breadcrumbs on deeper content types
- Fast, server-rendered access to critical copy without requiring motion or client-side interaction
- Complete 404, error, loading, and retry behavior without indexable placeholder copy

### Social previews

- Dedicated social asset where available; approved site-default fallback otherwise
- Title and description consistent with visible content
- No concept render presented as a completed RENZ project
- Appropriate image crop, dimensions, credit, and rights state

## Local relevance strategy

**Brief-supplied:** The company is described as Rwanda-based, and the brief includes Rwanda and Kigali query ideas.

**Publish gate:** Confirm the official physical location, service areas, phone, hours, public email, domain, and whether RENZ legitimately serves each named location.

After confirmation:

- Keep the name, address, phone, hours, and URL consistent across the site and approved business profiles.
- Use the authoritative details from one company-settings source.
- Describe service areas in helpful prose rather than repeating city names in headings.
- Associate projects with public-safe locations to demonstrate genuine relevance.
- Link to an official business profile only if it exists and is controlled by RENZ.
- Do not create city pages without distinct services, evidence, and local usefulness.
- Do not use hidden location lists, fake office addresses, or location markup unsupported by operations.

## Editorial content strategy

### Content pillars

1. **Preparing to build in Rwanda** — project readiness, information to gather, decision sequence
2. **Architecture and structural design explained** — briefs, dependencies, deliverables, coordination
3. **Cost planning and decision readiness** — cost inputs and estimate stages without unsupported price claims
4. **Construction and project control** — process, supervision, quality, safety, and communication when verified
5. **Renovation, interiors, and long-term performance** — assessment, disruption planning, durable choices
6. **RENZ project stories** — verified case studies and stage journals with clear RENZ roles

### Recommended initial backlog

These are **recommendations**, not finished headlines or claims:

- What to prepare before starting a construction project in Rwanda
- How to create a useful brief for house plans
- Why land surveying may be needed before design
- What structural design requires from a client
- What affects a construction cost estimate, without publishing unsupported rates
- Renovate or rebuild: questions that help frame the decision
- Managing a Rwanda building project from abroad, based on RENZ’s actual reporting process
- What project supervision includes, after scope verification
- How residential and commercial project preparation differ
- Verified project case studies as soon as evidence and media permissions are complete

### Editorial quality bar

Every article should:

- Answer one real user question directly
- State its scope and assumptions
- Use plain language and define technical terms
- Identify a real author and/or reviewer only when approved
- Record sources internally and expose useful citations where appropriate
- Show publish and updated dates accurately
- Link to a relevant service and next step without turning the article into an advertisement
- Receive a future review date when the subject can change

For regulations, permitting, costs, safety, and compliance:

- Assign a qualified reviewer.
- Record dated sources.
- Distinguish general preparation guidance from legal or professional advice.
- Update or unpublish content that cannot be kept current.
- Do not imply RENZ holds a license or regulatory authority because it discusses the subject.

## Internal linking model

```text
Insight preparation question
  → canonical Expertise page
  → verified relevant Project
  → Start a Project with context
```

Additional rules:

- Expertise pages link laterally only when services genuinely depend on or complement one another.
- Project pages link to the services RENZ actually performed, not every service that could apply.
- Articles link to source concepts and related current articles; avoid mechanically inserted keyword links.
- Related-project fallback uses shared service or project type only among published records; manual curation takes priority.
- Contact remains available as a lower-friction alternative at every high-intent point.
- Broken or unpublished internal relationships are surfaced in admin before publication.

## Localization readiness

**Recommendation:** If English is the only launch language, keep canonical URLs unprefixed unless a second language is imminent and a prefixed strategy is deliberately chosen.

The content model should still support:

- Locale-specific titles, slugs, body, metadata, alt text, and social copy
- Translation groups connecting equivalent records
- Translation states: missing, draft, in review, approved, published, stale
- Source locale and source-version relationship
- Locale-specific canonicals and sitemaps
- `hreflang` only between real, published equivalents
- A self-referencing language annotation for each published locale variant
- A deliberate default-language/fallback strategy

Do not expose a language switcher to nonexistent or incomplete translations. Do not serve English content at a URL presented as Kinyarwanda or French. Language priority is a **publish gate** requiring client and audience input.

## Content governance

### Ownership

Recommended accountable roles, to be assigned to real people:

- Business fact owner
- Service subject reviewer
- Project fact owner
- Media-rights/consent owner
- Editorial author/editor
- Publisher
- Legal/privacy reviewer

One person may hold multiple responsibilities, but the system should record the responsibility, not assume it from a job title.

### Review cadence

Avoid an arbitrary publishing quota. Prefer fewer maintained articles and complete case studies over frequent thin content.

Recommended review triggers:

- Credential or consent expiry
- Change to service scope or service area
- Regulation, process, or cost-source change
- Project status or public-permission change
- Contact/company detail change
- Broken relationship or media-rights change
- Scheduled factual review date

Expired claims should be removed or hidden automatically where safe and placed into a visible admin review queue.

## Measurement and privacy

**Recommendation:** Measure user decisions without sending inquiry content or personal data to analytics.

Suggested event families:

| Event | Purpose | Data minimization rule |
|---|---|---|
| `expertise_viewed` | Understand service interest | Service identifier only; no user-entered values |
| `project_viewed` | Measure portfolio engagement | Published project identifier only |
| `start_project_opened` | Measure high-intent entry | Origin route/service identifier |
| `start_project_step_completed` | Identify aggregate wizard friction | Step number/name only; never field contents |
| `project_request_submitted` | Measure conversion | Success state and non-personal origin context only |
| `contact_submitted` | Measure lower-friction conversion | Inquiry type only if approved and non-sensitive |
| `whatsapp_clicked` | Measure channel preference | Origin route only |

Analytics is non-blocking and consent-aware according to the eventual privacy policy. Admin, preview, and staff traffic should be excluded where practical. Search Console and privacy-conscious analytics can later validate query/page hypotheses; no ranking or traffic outcome is promised.

## Pre-publication SEO checklist

- Page is published, substantive, and intended for indexing
- Canonical URL is correct and uses the approved host
- Unique title and description accurately match visible content
- One logical H1 and clear heading structure
- All claims pass evidence and consent gates
- Media rights, alt text, crop, and social preview are approved
- Related links resolve to published canonical destinations
- Structured data matches visible content and passes syntax validation
- Page is included or excluded from sitemap intentionally
- No preview token, filter parameter, draft content, or personal data is exposed
- Mobile content and navigation remain complete with motion and JavaScript enhancements unavailable
- Regulatory or time-sensitive content has a current reviewer and review date
